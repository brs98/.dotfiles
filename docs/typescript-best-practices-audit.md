# TypeScript best-practices audit

Implementation status: the recommendations in this historical audit have been applied to [the skill](../skills/typescript-best-practices/SKILL.md). The 108 original entries are corrected or canonical cross-references, with five additional references covering missing topics. Compiler examples and local links now have repeatable validation scripts.

Independent follow-up review found no substantive false teaching claim in the updated reference, but identified nine counterexamples across eight TypeScript Doctor advisory detectors. Targeted guidance now explains derivation cycles, declared callable signatures, effective readonly modifiers, and the `keyof` difference between string index signatures and `Record`. This status describes the reviewed examples and documented conditions; it does not certify arbitrary transformations or the separate detector implementation. The original observations below are retained as historical findings.

Follow-up validation: 112 TypeScript blocks in 102 example projects compiled with TypeScript 5.9.3; all 113 reference entries and local links passed validation, as did the skill metadata check.

Reviewed 2026-09-04 against dotfiles commit `3ab561c`.

The skill contains useful examples, but it is not yet reliable as a set of mandatory coding rules. The most significant defects are incorrect inferred-type comments, unsafe helper contracts, valid alternatives labeled Bad, and course examples generalized beyond their intended context.

All **108 rule files** and the skill index were reviewed. File-level dispositions: **26 Fix, 47 Clarify, 31 Keep, 4 Merge**. These counts describe files, not independent bugs; some Fix/Clarify files also participate in suggested consolidations.

- **Fix:** change a false claim, broken example, unsafe recommendation, or consequential missing precondition.
- **Clarify:** keep the core pattern but narrow its scope or explain an important limitation.
- **Keep:** no substantive correction required; optional example cleanup is called out separately.
- **Merge:** consolidate duplicated guidance while retaining useful examples.

The detailed tables below cover every file exactly once and give concrete changes and supporting evidence. Only this report was added; the skill itself has not been rewritten.

## Sources and scope

I read the lesson open in the user's Chrome tab and inspected its course navigation. The linked page is the introduction to the larger workshop, so it cannot by itself support all 108 rules. The comparison uses relevant public workshop lesson transcripts and solutions, the [course-linked exercise repository](https://github.com/total-typescript/pro-essentials-workshop/tree/7491e6c5ed45dfcb3593289397e3a68244898128), and current first-party TypeScript/tool documentation. The course repository was inspected at commit `7491e6c5ed45dfcb3593289397e3a68244898128`; its package manifest declares TypeScript `^5.5.2`. This was a rule-by-rule audit, not a claim to have watched every course video.

The introduction frames TypeScript as development tooling over JavaScript. That distinction is particularly relevant to this skill's assertions, readonly rules, declaration files, and emitted syntax. [Original lesson](https://www.totaltypescript.com/workshops/typescript-pro-essentials/kickstart-your-typescript-set-up/typescripts-relationship-with-javascript).

I distinguish direct course mismatches from additional production guidance and updates since the course. For example, the early JSON lesson does use a variable annotation; recommending validation at an external-data boundary is an extension of that lesson's scope, not a claim that its solution was different.

## Changes to the skill's structure and index

1. **Correct the quick reference alongside each file.** It currently says “deep immutability,” “don't destructure,” and “never” where the detailed rule needs a conditional policy. Its `never` and switch summaries also promise exhaustiveness that the examples do not enforce. The index has disproportionate influence because an agent may read it without opening every rule.
2. **Replace universal Bad/Good labels for valid alternatives.** Annotation versus inference, getters versus methods, constructor initialization, same-name factories/types, inheritance, explicit type arguments, and development checking workflows are contextual choices. Use “Use when,” “Alternative,” and “Avoid when” where appropriate.
3. **Make every example self-contained and identify its environment.** State compiler/version assumptions, host libraries, relevant flags, and file boundaries. Separate alternate declarations instead of redeclaring names in a single block. Use expected-error markers for actual negative examples. With the skill's recommended `noUncheckedIndexedAccess`, some existing index-type comments need `undefined`.
4. **Record provenance and verification.** Give each rule a course lesson/source link, an applicable-version note where behavior changed, and a small checked example for factual claims. Keep source attribution separate from this repository's chosen conventions. A minimal example checker is a useful later implementation step; this review did not add a test framework.
5. **Merge repeated concepts.** Consolidate the two predicate files, the two StrictOmit files, the two interface-composition rationales, and the duplicate `noEmit` rules. Narrowing `instanceof` and catch handling can share a canonical explanation. Preserve unique examples and update references/counts after consolidation.
6. **Reassess priority labels.** Correctness and unsafe runtime assumptions deserve high priority. Blanket CRITICAL labels for all narrowing/readonly choices, with `strict` only MEDIUM, blur what an agent must fix versus what it should consider. Move editor shortcuts to a compact tooling reference if reducing context load is a goal.

These are audit recommendations, rather than claims that the course dictates this particular skill format.

## Verification

Focused compiler probes passed using both **TypeScript 5.5.2** (the course manifest's lower version) and the transient package that reported **7.0.2** during this audit. These were targeted checks of disputed behavior, not a compile of every illustrative snippet. The runs used strict checking, explicit targets, and isolated temporary files; declaration probes explicitly kept `skipLibCheck: false`. No repository dependencies or package-manager settings were changed.

Confirmed findings include inferred predicates, correlated destructuring, preserved closure narrowing, `satisfies` value widening, flat freeze literals, mutable referenced arrays under `as const`, `Omit` yielding `{}`, the `keyof object`/`never` predicate, optional generic defaults, structural extra keys, valid ambient literal constants, and implicit NodeNext resolution. Additional strict probes checked ignored callback returns, `implements` accepting extra methods, the limits of `noImplicitOverride`, symbol keys in string-only empty records, and the actual `fetch` parameter mismatch.

Representative observed results:

```typescript
// Emitted types from the skill's expressions:
const isStringArray = (value: unknown) =>
  Array.isArray(value) && value.every(item => typeof item === "string");
// inferred: (value: unknown) => value is string[]

const config = { apiUrl: "/api" } satisfies Record<string, string>;
// inferred: { apiUrl: string }

const frozen = Object.freeze({ api: "/api", version: 1 });
// inferred: Readonly<{ api: "/api"; version: 1 }>

const items = [1];
const wrapper = { items } as const;
wrapper.items.push(2); // accepted
```

Runtime probes also demonstrated that the supplied generic state setter leaves its exposed value `undefined`, the generic key predicate can report a static `"name"` while its runtime value is `"age"`, and a JSON annotation claiming a string can actually contain a number. These distinguish harmless style differences from misleading safety claims.
